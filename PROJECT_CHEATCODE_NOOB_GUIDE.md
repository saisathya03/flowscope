## 1. Project in One Sentence

**FlowScope AI takes records of data moving between backend systems, draws that movement as an animated 3D city, uses machine learning to find unusual behaviour and forecast the next interval, lets you test "what if" conditions, and shows recommended actions.**

Three words that are easy to mix up. Keep them separate:

| Word | Meaning here | Example |
|---|---|---|
| **Data Movement** | The **concept** we want to understand. Data leaving one system and arriving at another. | Development sends a build to the API Gateway |
| **Network Traffic Data** | The **measurement** of that movement. One row of numbers per observation. | 101.49 MB at 337 Mbps with 33.7 ms delay |
| **Network City** | The **place we show it**. Buildings are systems, bridges are routes, particles are data. | A copper tower sends glowing dots across a glass bridge |

The five jobs the project does:

1. **Data source** — network-flow telemetry, currently synthetic, in `data/network_traffic.csv` and `.json`.
2. **Visual representation** — the 3D Network City built by `js/app.js` using Three.js.
3. **Analysis, anomaly detection and prediction** — `python/analyze_and_predict.py` using scikit-learn.
4. **What-If simulation** — the branch inside `js/app.js` that tests conditions before acting.
5. **Decision support** — recommendations shown in the right panel and inside the story.

**One honest sentence to remember:** *It is a local, offline prototype running on generated data. It does not watch, control or connect to any real company network.*

## 2. What Real-World Problem Are We Solving?

Inside any company, systems talk to each other all day. An application calls an API gateway, the gateway calls a server, the server queries a database, results go to the cloud and to an AI service. That conversation never stops.

**Why this is hard to understand today:**

- **Logs** are millions of text lines. You must already know what to search for.
- **Tables** show numbers but not shape. You cannot see that three systems all depend on one server.
- **Numbers alone** hide direction. A latency of 185 ms does not tell you *which way* the data was going.
- **Monitoring dashboards** show one metric per box. Connecting ten boxes into one story is done in your head.
- Most importantly, **the movement itself is invisible**. Nobody can point at a screen and say "the data is stuck *there*".

**What FlowScope AI does about it:** it turns each flow record into something you can literally watch. A route that is busy has more and bigger particles. A route in trouble turns red and pulses. The system predicted to overload first gets a pulsing ring and a "BOTTLENECK" label. A manager, a developer and a network engineer can all look at the same picture and agree on where the problem is.

**Planned / Conceptual — not currently implemented:** feeding this with a real company's live telemetry. Today the data is generated by a Python script.

## 3. Overall Architecture

```
Network Flow Data          data/network_traffic.csv  +  .json   (360 rows)
        ↓
Aggregation                Python groupby, and aggregateData() in js/app.js
        ↓
Analysis                   totals and averages -> the KPI numbers
        ↓
Anomaly Detection          Isolation Forest (scikit-learn)
        ↓
Prediction                 4 x Random Forest Regression  (+ documented demo floors)
        ↓
Recommendation             6 if/else rules in recommendations_for()
        ↓
What-If Simulation         classifyIssue + projectUnderTraffic + simulateAlternative in js/app.js
        ↓
3D Network City            Three.js scene built by js/app.js
        ↓
Human Decision             a person reads it and decides. Nothing is automated.
```

**Each stage in beginner language:**

**Network Flow Data.** A table. Each row says "at this time, system A sent this much data to system B, and here is how it behaved". 360 rows covering three days.

**Aggregation.** Raw rows are grouped. Python groups by source and destination to find the busiest and most congested routes. The browser does the same in `aggregateData()`, producing 24 routes and 16 node summaries.

**Analysis.** Simple sums and averages: total megabytes, average latency, average load. These become the cards along the top of the screen.

**Anomaly Detection.** A model looks at all the rows and points at the ones that look strange compared with the rest. It is not told the answer beforehand.

**Prediction.** A second model looks at a system's current row and estimates what its next interval will look like: volume, load, latency and bandwidth.

**Recommendation.** Plain rules. "If any row is labelled API Overload, then recommend increasing gateway capacity." No machine learning here.

**What-If Simulation.** Before acting, ask "what happens if this gets worse?" and "what happens if we use a different route?". The answer is calculated, then compared side by side.

**3D Network City.** All of the above is turned into buildings, bridges, particles, colours and floating cards.

**Human Decision.** The project stops here on purpose. It advises; a person acts.

## 4. What Is Running on Localhost?

This section matters most, because it is the question people ask first.

### What is localhost?

`localhost` means **this computer**. It is a name that always points back to the machine you are sitting at. `http://localhost:8000` means "ask a program running on my own computer, on door number 8000, for a web page". Nothing leaves the machine. No internet is involved.

### Why do we need a local HTTP server at all?

You cannot just double-click `index.html`. Modern browsers block two things when a page is opened directly from a file:

1. **`fetch()` of local files.** `js/app.js` calls `fetch('./data/network_traffic.json')` and `fetch('./data/ml_results.json')` on lines 142 and 143. From a `file://` page the browser refuses this for security.
2. **JavaScript modules.** `index.html` loads the app with `<script type="module" src="./js/app.js">`. Modules are also blocked on `file://`.

So we run a tiny web server that does nothing but hand files to the browser:

```
python -m http.server 8000
```

That is the whole content of `run_windows.bat` and `run_mac_linux.sh`. It serves files. It has no database, no login, no logic. **It is a file server for a prototype, nothing more.**

### Who does what

| Part | File | Job in one line |
|---|---|---|
| **The page skeleton** | `index.html` | Defines every box on screen: loading screen, top KPI cards, left control rail, the 3D stage, right AI panel, status bar, dialogs. It contains no logic. |
| **The brain** | `js/app.js` | Loads the data, calculates route and node summaries, builds the 3D scene, runs the story, handles every click. |
| **The 3D engine** | `js/vendor/three.module.js` and `three.core.js` | The library that actually draws triangles on the screen. Also `OrbitControls.js` for mouse camera control and the `postprocessing/` files for the glow. |
| **The chart** | `js/vendor/chart.umd.js` | Draws the small 12-hour trend line in the right panel. |
| **The styling** | `css/styles.css` | Colours, fonts, panel positions, the immersive layout used in city mode. |
| **The data** | `data/network_traffic.json` | 360 flow records the browser reads. `data/network_traffic.csv` is the same data for Python. |
| **The analysis output** | `data/ml_results.json` | Everything Python worked out: KPIs, model scores, predictions, recommendations, alerts, the trend, the prepared alternative path. |
| **The data maker** | `python/generate_dummy_data.py` | Run by hand, beforehand. Creates the 360 synthetic records. |
| **The analyst** | `python/analyze_and_predict.py` | Run by hand, beforehand. Reads the CSV, runs the two models, applies the rules, writes `ml_results.json`. |

**Important:** the Python scripts are **not** running while you look at the page. They ran earlier and left a JSON file behind. The browser just reads that file.

### What happens from opening localhost to seeing the city

This is the real sequence, verified in `main()` at the bottom of `js/app.js`:

```
Browser opens http://localhost:8000
   → the local server hands over index.html
   → index.html loads styles.css, chart.umd.js, then js/app.js as a module
   → js/app.js runs main()
        1. loadData()            fetch network_traffic.json + ml_results.json
        2. aggregateData()       build 24 route summaries and 16 node summaries
        3. selectSituation()     pick the record for the 12-step situation story
        4. populateFilters()     fill the department dropdown
        5. populateDashboard()   KPI cards, predictions, recommendations, alerts, chart
        6. initThree()           create scene, camera, lights, then build:
                                   buildCityEnvironment()  water, sky, mountains, islands
                                   buildNodes()            the 16 buildings
                                   buildCurrentFlows()     bridges, arcs, particles
                                   buildPredictedFlows()   the purple suggested path
                                   buildFlowRiver()        the alternative river view
                                   buildSplatScene()       the experimental splat view
                                 then it switches to NETWORK CITY and starts animate()
        7. bindUi()              attach every button and slider
        8. startSimulationClock() the clock in the top bar starts ticking
        9. after 450 ms  the loading screen fades
       10. after 1100 ms startSystemFlow() begins the guided story
```

**State it plainly in your presentation:** *"Localhost is only hosting the prototype's files on my own laptop. The visualisation is reading a generated dataset. It is not connected to any real company network, and nothing here can change any real system."*

## 5. Dataset Explained Like I Am a Beginner

### What does one row mean?

**One row = one observation of data moving from one system to another, during one time slot.**

It is not one packet. It is not one user. Think of it as a summary line written every 12 minutes for one route, like a delivery log entry: "between 07:00 and 07:12, this much went from here to there, and this is how the trip went".

Facts about the file, from `python/generate_dummy_data.py`:

| Property | Value |
|---|---|
| Rows | 360 (`RECORD_COUNT = 360`) |
| Columns | 28 |
| Time covered | 2026-08-25 06:00 to 2026-08-28 05:48, one row every 12 minutes |
| Random seed | 42, so the file is identical every time it is regenerated |
| Systems | 16 |
| Routes | 24 unique source to destination pairs |
| Problem rows | 28, one injected in every 13th row, cycling through 9 problem types |

### Every important field

**Who and where (identity):**

| Field | Beginner meaning |
|---|---|
| `timestamp` | When this was observed. |
| `source_id` | Which system **sent** the data. Example: `Development`. |
| `source_type` | What kind of system that is: Department, API, Server, Database, Cloud, AI, IoT or Security. |
| `source_department` | Which team owns the sending system. |
| `destination_id` | Which system **received** it. Example: `API-Gateway`. |
| `destination_type` | The kind of system that received it. |
| `destination_department` | Which team owns the receiving system. |

**How much and how fast (performance):**

| Field | Beginner meaning | Everyday comparison |
|---|---|---|
| `data_volume_mb` | How many megabytes moved in that slot. | How many boxes were delivered. |
| `transfer_speed_mbps` | How fast it moved, megabits per second. | How fast the van drove. |
| `bandwidth_usage_percent` | How much of the road's capacity was in use, 0 to 100. | How full the road was. |
| `latency_ms` | Network delay in milliseconds. | Travel time on the road. |
| `packet_loss_percent` | Share of data that never arrived. 100 means the link failed. | Parcels lost on the way. |
| `network_load_percent` | How stressed the systems involved were, 0 to 100. | How busy the warehouse was. |
| `active_connections` | How many connections were open at once. | How many delivery vans were out. |

**How well it was handled (processing):**

| Field | Beginner meaning |
|---|---|
| `response_time_ms` | The full application turnaround, always larger than latency. |
| `queue_length` | How many requests were waiting to be processed. A traffic jam indicator. |
| `processing_rate` | How fast the receiving system was getting through work. |

**What kind of work it was (workload):**

| Field | Beginner meaning |
|---|---|
| `api_requests` | Number of API calls in that slot. |
| `database_queries` | Number of database operations. |
| `ai_requests` | Number of AI or analytics operations. |
| `iot_messages` | Number of device or sensor messages. |

**Who is allowed to see it (security and governance):**

| Field | Beginner meaning |
|---|---|
| `data_priority` | Low, Normal, High or Critical. How urgent the delivery is. |
| `data_classification` | Public, Internal, Confidential or Restricted. How sensitive the content is. |
| `access_permission` | Open, Employee, Role-Based, Privileged or Denied. Who may access it. |
| `threat_level` | Low, Medium, High or Critical. The security risk of this flow. |

**Was it healthy (status):**

| Field | Beginner meaning |
|---|---|
| `connection_status` | Connected, Degraded or Failed. |
| `route_status` | Optimal, Congested, Rerouted or Blocked. |

**The answer key (label):**

| Field | Beginner meaning |
|---|---|
| `anomaly_status` | `Normal`, or one of nine problem names: High Latency, Server Overload, Packet Loss, Traffic Spike, Failed Connection, Network Congestion, Suspicious Traffic, API Overload, Database Overload. |

**Very important about `anomaly_status`:** this label was written **by the data generator**, not by the AI. The Isolation Forest never sees it. Say "these 28 are labelled problem events in the dataset" and not "the AI found these 28".

### A real row, explained word by word

This is line 7 of `data/network_traffic.csv`, exactly as it exists:

```
2026-08-25T07:00:00Z, Development, Department, Development, API-Gateway, API, IT,
101.49, 337.01, 36.63, 33.73, 0.05, 33.67, 220, 51.28, 2,
Critical, Confidential, Role-Based, Low, Connected, Optimal,
237.65, 402, 22, 8, 2, Normal
```

Read as a sentence: **At 7 in the morning on 25 August 2026, the Development department sent 101.49 megabytes to the API Gateway, which the IT department owns. It travelled at 337 Mbps and used 36.6 percent of the available bandwidth. The delay was 33.7 milliseconds and almost nothing was lost, only 0.05 percent. The systems were at 33.7 percent load with 220 connections open, and the application answered in 51.3 milliseconds with only 2 requests waiting. The content was marked Critical priority and Confidential, so it needed role-based access. The security risk was Low, the connection was healthy, and the route was optimal. The receiving side processed about 238 records a second, and the traffic was made up of 402 API calls, 22 database queries, 8 AI requests and 2 device messages. Nothing was wrong with this observation.**

And here is a **problem** row, line 93, the one the demo story uses:

```
2026-08-26T00:12:00Z, API-Gateway, API, IT, Server-02, Server, Operations,
118.6, 562.13, 32.56, 44.56, 0.23, 95.52, 228, 170.9, 51,
Normal, Restricted, Privileged, Medium, Degraded, Optimal,
524.55, 321, 10, 15, 2, API Overload
```

The numbers that matter: **network load is 95.52 percent**, **51 requests are queued**, the application now takes **170.9 milliseconds** to answer, the connection is **Degraded**, and the row is labelled **API Overload**. That is the trouble the What-If branch reacts to.

## 6. Why Are There Particles?

### The single most important sentence

**A particle is a visual representation of measured data movement. It is not necessarily one network packet.**

If someone asks "is that one packet?", the honest answer is: no. Each route draws between 3 and 14 particles, and the number is calculated from the route's average megabytes. One particle stands for a share of the traffic, not for a countable unit.

### What the code actually maps

These are the real formulas from `js/app.js`. Nothing here is invented.

| What you see | Which field drives it | The actual code | Where |
|---|---|---|---|
| **Particle size** | `data_volume_mb` | `size = (.26 + clamp(volume / 2600, .02, .18))` | `addConduit()` line 2872 |
| **How many particles** | `data_volume_mb` | `count = clamp(round((volume / 45) * density), 3, limit)` | `addConduit()` line 2871 |
| **Particle speed** | `transfer_speed_mbps` | `speed = .03 + route.speed / 9000` | `addConduit()` line 2883 |
| **Direction** | `source_id` to `destination_id` | the particle's `phase` goes 0 to 1 along a curve that starts at the source and ends at the destination | `animate()` |
| **Density thinning** | how busy the two endpoints are | `density = clamp(1.18 - overlap * .05, .5, 1)` | `buildCurrentFlows()` |
| **Route thickness** | `bandwidth_usage_percent` | `radiusScale = .8 + clamp(bandwidth / 100, 0, 1) * .7` | `buildStoryRoute()` line 5040 |
| **Route glow** | `network_load_percent` | `glowScale = .6 + clamp(networkLoad / 100, 0, 1) * 1.2` | `buildStoryRoute()` line 5040 |
| **Colour** | status fields | `flowColor()` | line 2688 |

### Tiny examples

**Low volume.** The real route `API-Gateway → Security-Hub` averages 68.5 MB. That gives `round(68.5 / 45) = 2`, raised to the minimum of 3 particles, each sized `.26 + 68.5/2600 = 0.29`. You see a thin, quiet trickle.

**High volume.** The real route `API-Gateway → Server-03` averages 339 MB. That gives `round(339 / 45) = 8` particles before the density factor is applied, each sized `.26 + 339/2600 = 0.39`. You see a thick, busy stream of bigger dots.

**Fast versus slow.** At 562 Mbps a particle advances `.03 + 562/9000 = 0.092` of the route per second, so it crosses in about 11 seconds. At 163 Mbps it advances `0.048`, taking about 21 seconds. The audience sees the difference without reading a number.

### Two honest footnotes

- **Thickness and glow are only data-driven on the story routes**, the river tubes and the splat view. The ordinary bridges in the free-explore city use a **fixed** thickness of 0.36 and a fixed glow. There, load and bandwidth are communicated through colour and through the inspector panel instead.
- **Density is thinned, not increased, at busy hubs.** The `density` factor drops as low as 0.5 when many routes touch the same building, so the picture stays readable. That is a legibility choice, not a data statement.

## 7. Network City Explained

### Why a city?

Because a building has a **place**, a **size**, **lights** and a **state**, and so does a computer system. You can look at a building, walk around it, click it, and see at a glance whether it is lit red. A table of numbers cannot do that.

The layout is fixed by hand in the `NODE_CONFIG` array at the top of `js/app.js`, positioned to match `reference-network-city.png`. Positions are **not** calculated from data. The 16 buildings sit on 13 hexagonal islands in a night harbour, joined by glass bridges.

### Every building in the project

| Building | Represents | What it does | Animation it shows | Data in | Data out | If it has a problem |
|---|---|---|---|---|---|---|
| **Development** (also **QA**, **HR**, **Finance**, **Management**) | A department using applications | Creates requests and files | Monitors blink, windows light, a glowing package appears and moves to the entrance | nothing (it is a starting point) | to API-Gateway, Server-01, Database-01, AI-Engine | Its route turns yellow or red |
| **API-Gateway** | The front door for all requests | Checks and forwards requests to the right server | Portal opens, packet pauses in the ring, two scanner rings spin, `AUTH ✓` then `ROUTE ✓` then `ACCEPTED` appear | from departments | to Server-01, 02, 03, and Security-Hub | Packets stack in front of it, the pulse turns yellow then red |
| **Server-01 … Server-04** | Machines running application logic | Process requests and call databases | Rack LEDs light bottom to top, a core spins, data lines climb the facade, a progress arc fills | from the gateway, HR, IoT | to the databases and the cloud | LEDs go cyan then yellow then red, a heat shimmer appears, waiting packets form a queue lane |
| **Database-01, Database-02** | Where data is stored | Answer queries, save records | Rings light top to bottom, a glowing cube drops into the vault, rings squeeze, a green spark and expanding ring confirm | from servers, Finance, gateway | to AI-Engine | Rings flash yellow or red, the queue grows |
| **Cloud-01** | Externally hosted services | Receives and stores results | Intake ring, upload 25 → 60 → 85 → 100 percent, then a **white** success burst | from servers, AI, IoT, Security | to Management | Turns yellow, then red. It does **not** show the white glow |
| **AI-Engine** | The analytics and model service | Analyses data and predicts load | Purple particles spiral inward, an orbit ring turns, a small waveform appears | from the databases and Management | to Cloud-01 | Route turns purple-red, no special failure animation |
| **Security-Hub** | Security inspection | Scans traffic, allows or blocks | A laser sweeps up and down, a shield appears, green if safe, red if blocked | from API-Gateway | to Cloud-01 | The shield turns red, the packet stops, the route turns red |
| **IoT-Gateway** | The gate for devices and sensors | Collects sensor messages, merges them | Six small sensors emit dots that fly in and merge into one bigger packet | from sensors | to Server-02 and Cloud-01 | The destination shows a warning or failure state |

### Two colour systems, kept separate

This is important and often confused.

- **Building colour = who owns it.** A muted architectural tone from `DEPARTMENT_COLORS`, shown on windows, trim, edge lights and signage. Copper for Development, gunmetal for IT, bronze for Operations, and so on.
- **Flow colour = what is happening.** Blue, cyan, purple, yellow, red and green on the particles and routes.

They never mix. A copper Development tower can still send a blue normal flow and receive a red anomaly warning.

## 9. Building Functionality Animations

Every building performs its real job instead of sitting still. This is the `FLOW_PHASES` list in `js/app.js`, 15 phases driven by a controller class called `FlowSequence`.

| Building | Implemented behaviour | Phase id in the code |
|---|---|---|
| **Development** | Monitors blink, tower windows glow, a package is created, scaled up, and moved to the entrance. Message: "File ready for upload". | `CREATE_FILE` |
| **API Gateway** | **Receive** the packet, **authenticate** with a rotating scanner, **route** it, **accept** it. Three labels stack up: `AUTH ✓`, `ROUTE ✓`, `ACCEPTED`. The pulse is cyan when healthy, yellow under load, red when critical. | `API_AUTH`, `API_ROUTE` |
| **Server** | **Receive**, **queue** if `queue_length` is above 20 (waiting packets appear in an intake lane and are drawn in one by one), **process** with rack LEDs and a progress arc, **complete** with "Business logic completed". | `SERVER_PROCESS`, `SERVER_RESPONSE` |
| **Database** | **Write**: rings light downward, a cube sinks in, rings compress, a green spark, then "Record Saved ✓". **Read**: rings light, a block rises out, then "Data returned" and it travels back. | `DATABASE_WRITE`, `DATABASE_READ` |
| **Cloud** | **Receive** with an intake ring, **upload** 25 → 60 → 85 → 100 percent, then **success**. | `CLOUD_UPLOAD`, `CLOUD_SAVED` |
| **AI Engine** | **Analyze**: purple particles spiral inward, neural links glow, a waveform appears. **Predict**: shows the stored forecast, then draws a translucent purple predicted route. | `AI_ANALYZE` |
| **Security Hub** | **Scan** with a moving laser and a shield hologram, then **allow** (shield turns green, "Security scan passed ✓") or **block** (shield turns red, packet stops, route turns red, "Threat detected"). | `SECURITY_SCAN` |
| **IoT Gateway** | **Collect**: six sensors emit dots that fly in and merge. **Send**: the merged stream goes to the destination named by the row. The count shown is the row's real `iot_messages` value. | `IOT_AGGREGATE` |

### The universal Cloud success rule

Cloud-01 has its own state controller, separate from the other buildings, in the "CLOUD OPERATION STATES" section of `js/app.js`. The states are set by `setCloudState()` and the values live in `CLOUD_TARGETS`:

| State | Colour | When |
|---|---|---|
| **IDLE** | Dark blue (`0x2f4f72`) | Nothing happening |
| **RECEIVING** | Blue / cyan, slow pulse | Data is arriving |
| **PROCESSING** | Brighter cyan, faster pulse | The operation is running |
| **SUCCESS** | **Bright white**, plus a soft white bloom, 3 to 5 white and cyan sparks, one expanding ring and a message | The operation **completed successfully** |
| **WARNING** | Yellow pulse | The cloud is under load |
| **FAILED** | Red pulse and a red ring | The operation failed |

**What the white glow means:** *"The current Cloud operation completed successfully."* It is deliberately triggered only by a real success, never merely because data arrived. The functions are `cloudOperationSuccess()` and `cloudOperationFailed()`, and they are reusable, so any future cloud operation gets the same feedback. You can test it from the browser console with `cloudOps.success('Cloud-01', 'Backup Completed ✓')`.

## 10. Color Cheat Sheet

There are **two independent colour systems**. Getting this right is the fastest way to sound like you understand the project.

### A. Flow colours — WHAT IS HAPPENING

Set by `flowColor()` in `js/app.js` line 2688, checked in this exact order:

| Colour | Hex | Meaning | The actual trigger |
|---|---|---|---|
| **Red** | `0xff3c4e` | Problem | The route is on the known bottleneck path, **or** its worst row has Critical threat / Suspicious Traffic / Failed connection, **or** it has an anomaly with average latency above 90, load above 78, or loss above 3 |
| **Green** | `0x2eea8b` | Recommended or successfully processed | The route is a recommended segment, or it is healthy and its index is divisible by 6 |
| **Yellow** | `0xffd426` | Critical priority delivery | The worst row's `data_priority` is Critical |
| **Purple** | `0xa45dff` | AI traffic, or a predicted / simulated route | The route touches AI-Engine, or it is a predicted or What-If route |
| **Cyan** | `0x39e7ff` | High-speed data | Average speed above 500 Mbps |
| **Blue** | `0x129cff` | Normal | Everything else |
| **White** | — | Cloud success only | Cloud-01 completed an operation |

### B. Department colours — WHO OWNS THE SYSTEM

From `DEPARTMENT_COLORS` in `js/app.js`. Applied only to window light, roof trim, edge lights and signage. Building bodies stay dark graphite and dark glass.

| Department | Colour | Hex | Buildings |
|---|---|---|---|

## 12. AI / ML Explained for a Noob

The project uses **two real machine-learning models**, both from scikit-learn, both run **offline** by `python/analyze_and_predict.py` before you ever open the browser.

### Isolation Forest — "Is something unusual happening now?"

**The idea without maths.** Imagine every observation as a dot in a space made of 14 numbers. Normal traffic forms a thick cloud of dots. Now play a game: cut the space with random lines, over and over, until one dot is alone in its own little box. A dot in the middle of the crowd needs many cuts. A dot far away from everyone gets separated after only a few. **Few cuts needed = unusual.**

| Question | Answer, from the code |
|---|---|
| **What goes in?** | The 14 numeric columns in `NUMERIC_COLUMNS`: volume, speed, bandwidth, latency, packet loss, load, connections, response time, queue, processing rate, and the API / database / AI / IoT counts. |
| **What does it check?** | How easy each row is to separate from all the others. It is **not** told which rows are problems. That is what "unsupervised" means. |
| **What are the settings?** | `IsolationForest(n_estimators=180, contamination=0.08, random_state=42)` — 180 trees, and it is told to expect about 8 percent unusual rows. |
| **What comes out?** | A flag per row: `-1` means unusual, `1` means normal. It flagged **29 of 360 rows**. |
| **Why do we need it?** | So the system can point at strange behaviour without anyone writing a rule for every possible failure. |
| **Where does it show up?** | In the alert list, and as the number `model_anomalies: 29` in `data/ml_results.json`. **Honest limitation: the per-row flags are not saved, so the 3D city cannot highlight exactly which rows the model picked.** |

**Do not confuse two numbers.** The KPI card says **28 anomalies** — those are the **labels the data generator wrote** in `anomaly_status`. The model separately flagged **29**. They are different things and the code never compares them.

### Random Forest Regression — "What may happen next?"

**The idea without maths.** A decision tree asks yes/no questions ("is it after midday?", "is the load above 60?") until it reaches a small group of similar past examples, then answers with their average. One tree guesses badly. A **forest** of 140 trees, each trained on a random slice of the data, averages out the mistakes.

| Question | Answer, from the code |
|---|---|
| **What goes in?** | Hour, minute, day of week, the 14 numeric columns, plus the identity of the source, destination, types, priority and threat level converted into 0/1 columns. |
| **What is it predicting?** | For each system, its **next** observation's `data_volume_mb`, `network_load_percent`, `latency_ms` and `bandwidth_usage_percent`. That is four separate models. |
| **What are the settings?** | `RandomForestRegressor(n_estimators=140, max_depth=12, min_samples_leaf=2, random_state=42)` |
| **How was it tested?** | Trained on the first 80 percent of rows in time order, tested on the last 20 percent. |
| **How good is it?** | **Honestly, weak on this data.** The R² scores in `ml_results.json` are 0.11, −0.01, −0.06 and 0.19. A score near zero means the forecast is not much better than guessing the average. That is expected, because the synthetic rows are generated independently and there are only 275 training rows. |
| **Where does it show up?** | The "PREDICTED EVENTS" list in the right panel, and the risk badges. |

**The demo floors — say this before anyone finds it.** In `train_predictions()` there is a block called `scenario_floors`. For four systems (API-Gateway, Server-02, Database-01, Cloud-01) the predicted values are raised to a fixed minimum so the overload storyline is visible. That is why Server-02 shows exactly 91.2 percent. The JSON labels each prediction with `forecast_basis`, either `"Random Forest baseline"` or `"Random Forest + overload stress scenario"`. **Every Critical and Watch badge in the UI comes from those floors, not from the model.**

### Recommendation — "What action could we consider?"

**This is not machine learning.** It is six `if` statements in `recommendations_for()` in `python/analyze_and_predict.py`:

1. If any row is labelled API Overload, or the gateway's risk is not Stable → *"Increase API Gateway capacity and enable rate-based autoscaling."* (Critical)
2. If any row is labelled Database Overload → *"Optimize Database-01 queries and shift read traffic to Database-02."* (High)
3. If any row is labelled Suspicious Traffic → *"Investigate and isolate traffic from {source} to {destination}."* (Critical)
4. If any route status is Congested → *"Reroute Server-02 traffic through Server-04 to Database-02."* (High)
5. If Cloud-01's predicted load is above 80 → *"Scale Cloud-01 resources before the next forecast interval."* (Medium)
6. Always → *"Move low-priority internal traffic to lower-load routes during peak periods."* (Optimization)

Six are generated, and the UI shows the first four.

### The three questions, side by side

| | Question it answers | How it works here |
|---|---|---|
| **Anomaly detection** | "Is something unusual happening **now**?" | Real ML, Isolation Forest, unsupervised |
| **Prediction** | "What may happen **next**, if things carry on?" | Real ML, Random Forest, plus documented demo floors |
| **Recommendation** | "What **action** could we consider?" | Plain rules, no ML |

## 13. What-If Simulation

### What it means

**What-If asks: "what might happen if we change something?"** It does not measure. It calculates a projection so you can compare options **before** acting.

### The example built into the app

Server-02 is observed at **95.52 percent load** with **51 requests queued**.

**Question:** *"What if traffic to Server-02 increases by 50 percent?"*

The projection uses a simple, explainable queueing rule in `projectUnderTraffic()`. The idea in one line: **the busier a system gets, the faster delay grows, because delay behaves like 1 divided by the free capacity.** At 50 percent busy things are fine; at 95 percent a small extra push causes a big jump.

| | Load | Latency | Queue | Risk |
|---|---|---|---|---|
| **Observed now** | 95.5% | 45 ms | 51 | — |
| **IF NOTHING CHANGES (simulated)** | 99.5% | 399 ms | 476 | **CRITICAL** |
| **ALTERNATIVE via Server-04 (simulated)** | 66.0% | 66 ms | 3 | **MEDIUM** |

The alternative's starting point is **not invented**. Server-04's own observed traffic averages 42.1 percent load and 39 ms latency, and the simulation adds the extra demand on top of that. The card prints where the baseline came from and how much traffic was assumed to move.

Then the recommendation appears, the purple route turns green, and the story continues on Server-04 to Database-02.

### Visual states, exactly as implemented

| State | Colour | Meaning |
|---|---|---|
| Current healthy | Blue / cyan | Normal flow |
| Warning | Yellow | A threshold was crossed |
| Problem | Red | Critical, failed or a threat |
| Predicted / What-If | **Translucent purple, dashed** | A simulation. Never a measurement |
| Optimized / success | Green | The chosen option is now the active route |

### The rule you must never break

**Simulated data must never be presented as observed data.** The app enforces this. Under the panel note there is a coloured line that always says which class of number you are looking at:

| Label | Colour | Meaning |
|---|---|---|
| **OBSERVED** | Green | Read from a dataset row. Never modified. |
| **PREDICTED** | Cyan | From `ml_results.json`, the Random Forest output plus its demo floors. |
| **SIMULATED** | Purple | The What-If projection, calculated live. |

Every simulated card also carries a **SIMULATED** badge in its corner.

### The six scenarios in the code

| Scenario | Trigger | What it offers |
|---|---|---|
| **Server overload** | Load above 85, or a big queue, on a Server | Reroute to a lower-load server |
| **Database congestion** | Load, latency or queue high on a Database | Shift read traffic to the second database |
| **Server failure** | `connection_status` Failed or `route_status` Blocked | Reroute through a healthy peer |
| **API gateway overload** | Deep request queue while the target server is fine | Distribute requests, shed low-priority traffic |
| **Security threat** | Critical threat, Denied access, or Suspicious Traffic | **Block the route.** Flagged traffic is never rerouted. If nothing safe exists it says "No safe alternative available" instead of inventing one |
| **Cloud overload** | Load or latency critical on the Cloud | No peer cloud exists, so it simulates shedding 35 percent of low-priority demand on the same node |

## 14. Dynamic Story Mode

Story Mode is no longer a straight line. It checks the health of each hop and branches.

```
NORMAL FLOW
   ↓
CHECK HEALTH  (classifyIssue reads the active row)
   ↓
Healthy?  →  continue to the next phase
   ↓
Problem?
   ↓
ISSUE DETECTED     route thickens, turns yellow then red, message appears
   ↓
STORY PAUSE        particles freeze, CURRENT STATE card (OBSERVED)
   ↓
WHAT-IF            city dims, the question appears
   ↓
AI PREDICTION      IF NOTHING CHANGES card (SIMULATED)
   ↓
ALTERNATIVE        translucent purple route appears
   ↓
COMPARE            two-column before/after card
   ↓
RECOMMENDATION     action text, matched to a stored recommendation when possible
   ↓
APPLY              purple becomes green, old route fades, packet travels the new way
   ↓
SUCCESS            continue the story on the optimised route
```

**The thresholds that decide "problem"**, from `WHATIF_LIMITS` and `classifyIssue()`:

- `network_load_percent` above 85
- `bandwidth_usage_percent` above 85
- `latency_ms` above 120
- `packet_loss_percent` above 3
- `queue_length` above 30
- or `connection_status` is Failed or Degraded
- or `route_status` is Congested or Blocked
- or `threat_level` is Critical, or `access_permission` is Denied
- or `anomaly_status` is not Normal

**A guard worth knowing:** only **one** branch runs in the main flow, so the demo stays a single clear story. The Security Hub runs its own branch separately.

**There is also a second, older story** still in the app: the **12-step "Live Network Situation"**, reached from the `SITUATION` button. It walks through one real record from data generation to result. With the shipped dataset it picks the Suspicious Traffic row `Server-01 → Database-02` from 27 August and ends with "Critical issue requires manual investigation".

## 17. What Would Change in a Real Company?

**Today:**

```
generate_dummy_data.py  →  CSV / JSON files  →  python -m http.server 8000  →  browser  →  3D city
```

**In a real deployment:**

```
Authorised telemetry collectors
   (network flow exporters, router / switch / firewall counters, server monitoring,
    APM agents, API gateway logs, database monitors, cloud metrics, security tooling)
        ↓
Ingestion pipeline into a time-series store
        ↓
Scheduled or streaming analysis, models retrained on real history
        ↓
An authenticated internal API
        ↓
FlowScope front end
        ↓
Human approval before any action is taken
```

**What each field would come from:**

| Field group | Realistic source |
|---|---|
| volume, speed, bandwidth, latency, loss, connections, statuses | Network flow exporters, SNMP counters, load balancer and firewall logs |
| response time, queue length, processing rate, API / database / AI / IoT counts | Application performance monitoring, API gateway logs, database monitors, the IoT platform |
| priority, classification, permission, threat level | Data-loss-prevention tooling, identity and access management, the security information system, a data catalogue |
| `anomaly_status` | In production this would be a **model output**, not an input |

**What must be in place before any of that:**

- **Authorisation.** Written approval from IT security before collecting anything.
- **Authentication.** Single sign-on. The prototype has none, and the operator name in the corner is hard-coded text.
- **Access control.** Roles, and scoping by department so people only see what they should.
- **Privacy.** Only system-to-system metadata. **Never** message contents, documents, passwords, tokens, personal identifiers or anything about individual employees. The visualisation needs none of it.
- **Audit.** A record of who viewed what.
- **Human approval.** Any automated action must be reversible and approved by a person.

**Planned / Conceptual — not currently implemented:** every item in this section.

## 21. "If Sir Asks..." Viva Questions

**1. What is your exact project concept?**
FlowScope AI turns records of data moving between backend systems into an animated 3D city, so that invisible movement becomes visible. Machine learning finds unusual behaviour and forecasts the next interval, and a What-If layer lets you test conditions before acting. The output is a recommendation for a human to decide on.

**2. What problem are you solving?**
Backend data movement is normally understood through logs, tables and dashboards, which show numbers but not shape or direction. You cannot point at a screen and say "the data is stuck there". FlowScope makes the movement, its direction and its problems visible in one picture that a manager and an engineer can read together.

**3. Why 3D and not a normal dashboard?**
A dashboard shows one metric per box, so connecting ten boxes into one story happens in your head. In 3D you see the topology, the direction of travel, the volume and the health at the same time. The exact numbers are still available in the inspector panels, so we do not lose precision.

**4. Why a city metaphor specifically?**
A building has a fixed place, a size, lights and a state, and so does a computer system. That makes it natural to look at, walk around, click and judge at a glance. It also lets a non-technical audience follow the story without any training.

**5. Why particles?**
Because movement is the whole point, and a still picture cannot show movement. A particle carries four pieces of information at once: how much data, how fast, in which direction, and in what condition. That is far more than a number in a table conveys.

**6. Are the particles actual network packets?**
No, and this is important. A particle is a visual representation of measured data movement. Each route draws between 3 and 14 particles, and that count is calculated from the route's average megabytes, so one particle stands for a share of the traffic rather than a countable unit.

**7. Where does the data come from?**
Currently from `python/generate_dummy_data.py`, which creates 360 synthetic records with a fixed random seed of 42. Each row is one source-to-destination observation in a 12-minute slot, with 28 fields. In a real deployment the same 28-column shape would be filled from authorised monitoring systems.

**8. Is this real company data?**
No. It is entirely synthetic and generated on my own machine. It contains no real systems, no real traffic and no information about any person.

**9. Why localhost? What is it doing?**
Localhost simply means my own computer. We run `python -m http.server 8000` because browsers block `fetch()` of local files and JavaScript modules when a page is opened directly from disk. The server only hands over files; it is not connected to any network and holds no logic.

**10. Why Three.js?**
Three.js is the standard JavaScript library for 3D in a browser, so the project runs anywhere without installing anything. It is included locally in `js/vendor/`, so the whole prototype works with no internet connection.

**11. Why use AI at all? Could you not just use thresholds?**
Thresholds only catch the failures you already thought of. The Isolation Forest finds rows that are unusual compared with everything else, without being told what to look for. The Random Forest then estimates the next interval, which thresholds cannot do at all.

**12. Which machine learning algorithms are used?**
Two, both from scikit-learn and both run offline by `python/analyze_and_predict.py`. Isolation Forest for anomaly detection, and four Random Forest Regression models for prediction.

**13. Why Isolation Forest?**
It is unsupervised, so it needs no labelled examples, which matters because real failures are rare and rarely labelled. It works well on plain numeric tables and is fast. We give it the 14 numeric columns and it flags the roughly 8 percent most unusual rows.

**14. Why Random Forest Regression?**
It handles a mixture of numeric and categorical inputs, needs very little tuning, and resists outliers. We train four separate forests to predict the next interval's volume, load, latency and bandwidth for each system.

**15. What exactly is anomaly detection here?**
It answers "is something unusual happening now?". The Isolation Forest looks at each row's 14 numbers and flags the ones that are easiest to separate from the crowd. It flagged 29 of the 360 rows.

**16. What is prediction here?**
It answers "what may happen next?". For each system we take its most recent row and estimate the next interval's volume, load, latency and bandwidth. The results appear as the "PREDICTED EVENTS" list.

**17. How accurate is the prediction?**
Honestly, weak on this dataset. The held-out R² scores are 0.11, −0.01, −0.06 and 0.19, which means the forecast is barely better than guessing the average. That is expected, because the synthetic rows are generated independently and there are only 275 training rows.

**18. Then why do Server-02 and API-Gateway show Critical?**
Because of documented demo floors in the `scenario_floors` block. For four nodes the predicted values are raised to a fixed minimum so the overload storyline is visible in a demonstration. The JSON records this in a field called `forecast_basis`, and I would remove those floors before using real data.

**19. What is What-If Simulation?**
It answers "what might happen if we change something?". When a threshold is crossed, the story pauses, projects the problem forward, tests an alternative, and shows a before-and-after comparison so the better option can be chosen before acting.

**20. What is the difference between prediction and What-If?**
Prediction asks what may happen next if things simply carry on, and it comes from a trained model. What-If asks what may happen if a specific condition changes, such as traffic rising by 50 percent, and it is a calculated projection. Prediction is passive; What-If is a test you choose to run.

**21. How does the What-If calculate its numbers? Is it invented?**
No. It uses a queueing approximation where delay grows as one divided by the free capacity, which is why a system at 95 percent reacts badly to a small extra push. The alternative's starting point is that system's own observed traffic, and the card prints where the baseline came from and how much traffic was assumed to move.

**22. What is the recommendation engine?**
It answers "what action could we consider?". It is six deterministic `if` rules in `recommendations_for()`, based on the anomaly labels, the route status and the predicted load. **It is not a machine learning model**, and I would not describe it as one.

**23. Why does the Cloud glow white?**
White is the universal signal that the current cloud operation completed successfully. Dark blue is idle, cyan is processing, yellow is under load and red is failure. It is deliberately triggered only by a real success, never merely because data arrived.

**24. What happens during an overload?**
The route thickens and its particles slow down, the colour moves from cyan to yellow to red, waiting packets stack up in front of the building, and a red message names the issue. The story then pauses and shows the observed state before any simulation begins.

**25. Does the AI automatically reroute traffic?**
No. Nothing in the codebase makes a network call or changes any system. The word "reroute" only ever means that the story redraws itself along a different path.

**26. How would you connect this to a real company?**
Replace the generator with authorised collectors: network flow exporters, application performance monitoring, API gateway logs, database and cloud metrics and security tooling. Then add a data store, a scheduled analysis pipeline, an authenticated API and login. Models would be retrained on real history and the demo floors removed.

**27. Would you need employees' personal data?**
No, and we should not collect it. The visualisation works entirely at the system-to-system level, so it never needs message contents, documents, passwords, tokens or personal identifiers.

**28. What are the limitations?**
The data is synthetic and small at 360 rows, the analysis is offline rather than live, the forecast model is weak on this data, four nodes carry demo floors, there is no login and no automated tests. It also does not control anything, which is by design.

**29. What is unique about your project?**
It joins three things that are usually separate: a genuine data pipeline with real ML, a spatial visualisation where every building performs its actual function, and a What-If layer that tests options before acting. It also labels every number as observed, predicted or simulated, so the audience always knows what they are looking at.

**30. What is the final goal?**
To make invisible backend data movement visible, understandable and actionable. The 3D view is the communication layer; the goal is a faster and better human decision.

## 27. Final Mental Model

```
DATA            360 flow records, 28 fields each
   ↓
MOVEMENT        who sent what to whom, how fast, in what condition
   ↓
VISUALIZATION   buildings, bridges, particles, colour
   ↓
UNDERSTAND      one picture instead of ten dashboards
   ↓
DETECT          Isolation Forest finds the unusual rows
   ↓
PREDICT         Random Forest estimates the next interval
   ↓
SIMULATE        What-If tests a condition and an alternative
   ↓
RECOMMEND       rules turn the findings into an action
   ↓
DECIDE          a human reads it and acts
```

**In one paragraph:** We start with data about movement, because movement between systems is where performance and security problems actually live. We visualise that movement as a city so a person can understand it at a glance instead of reading ten dashboards. Machine learning then detects what is unusual now and predicts what may happen next. When something crosses a threshold, the What-If layer tests what happens if it gets worse and whether a different route would be better, and a rule engine turns that into a concrete recommendation. The chain deliberately ends at a human, because the purpose of the whole project is not to automate a decision but to make a good decision possible and fast.
